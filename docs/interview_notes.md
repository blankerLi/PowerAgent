# 面试准备：分层表述与深挖问答

这份文档是给自己用的准备材料，不是项目交付物。原则：**每个回答先给结论，再给可复算的依据**；限制主动说，不等对方问出来。

所有数字的来源都在 `artifacts/` 下，回答时可以直接指路。数字口径与 README 一致，两处不允许出现不同的说法。

## 一、30 秒电梯陈述

> 我做了一个 LLM 驱动的参数寻优 Agent，用在一个昂贵、会失败、带硬约束的电路仿真环境里。核心不是"让大模型给答案"，而是**建一套能约束住它、能审计它、也能证伪它的工程系统**：模型只负责提候选，全部安全判定和判分都在确定性代码里，被拒的候选带具名原因落库。
>
> 有效性我是拿数据说的：先把 144 点的设计空间穷举一遍建立参照系，然后只换提案来源、其余评价路径完全相同地跑对照——模型三次独立运行都命中了全域最优解，均匀随机五次一次都没命中。同时我也把限制写进了记录：这个空间只有 144 点，随机也能找到"够好"的解，样本量是 3 和 5。

**如果只能记一句**：这个项目证明的不是"LLM 很聪明"，而是"我有能力判断 LLM 到底有没有用"。

## 二、3 分钟项目介绍

**问题**（20 秒）
多相 Buck 供电模块的补偿网络整定：两个参数决定负载突变时电压掉多深、多久恢复、还剩多少稳定性裕量。评价一个候选要跑开关级仿真，单次 360 ms，且候选可能不可行——所以这是个"每次试错都要付费、还会失败"的搜索问题。传统做法是工程师凭经验试或者网格穷举。

**做法**（60 秒）
三个信任域，边界由包结构强制：

- **LLM 域**只能读状态、输出 3~6 个候选和一段搜索假设。不能调仿真、不能写状态、不能判分，**也不能决定自己被校验的严格度**。
- **确定性域**做全部安全判定：单位归一、合法域、档位对齐、新颖度、约束判定、worst-case 聚合、排序。
- **仿真域**是唯一有权访问模型文件的地方，寻优期只读。

关键的几个工程点：波形有 35007 个采样点，我不塞进 prompt，先确定性压缩成 6 个特征；相同状态产出逐字节相同的 prompt 和 `context_hash`；LLM 的两类失败（输出不合格式 vs 网络失败）分开计数分开处理；SQLite 是唯一事实源，进程崩了能从数据库重建搜索状态。

**结果**（40 秒）
模型三次运行都命中 144 点里的全域最优（`rcomp=28480.4 Ω, ccomp=100 pF` → 恢复时间 5.2 µs），随机五次排名是 2、2、4、5、23。候选一次通过确定性校验 15/15——档位值要求 7 位有效数字，我原本担心模型抄不准。

**最有意思的部分**（40 秒）
第一次跑参考扫描时，"最优解"落在设计域角点、恢复时间 2.2 µs，看起来很好。但我查了一下它的增益裕量，只有 1.9 dB——接近失稳。追下去发现硬约束里有相位裕量 45° 却没有增益裕量下限，而 45°/6 dB 是配对的判据，配置只写了一半。60 个"可行"点里 40% 增益裕量不足。

补上第五条约束后重跑，可行点从 60 降到 36，最优解换了位置。这件事让我确信这套系统是有用的——**最优化会精确地利用你没约束住的任何自由度**，而我能发现它，是因为端到端跑通了并且有参照系可比。

## 三、深挖问答

### A. 架构与信任边界

**Q：为什么要分信任域？直接调 LLM 然后校验一下不行吗？**

分域的意义在于**权限的缺失是结构性的**，不是靠代码里的 if 判断。举个具体的：校验器放在哪里。我把它放在 `controller` 层而不是 `agent.propose` 内部，因为如果校验在提案器里，被校验的一方就同时握有校验规则——"模型不能自己放宽约束"这条性质就只剩口头保证。现在的依赖方向是 `run_task → llm_propose → agent.propose`，校验器由 controller 调用，模型答什么都不会改变筛法。

同理，判分权在 `eval`，LLM 完全不参与约束判定和排序。它连"自己的候选有没有通过"都不知道，只能在下一轮从 `SearchState` 里读到结果。

**Q：那 LLM 到底做了什么？**

它做的是**在一个连续但有结构的搜索地形上选下一批探测点**。这个地形有几个特征：时域指标单调偏好一个角点，但那个角点会撞上增益裕量约束；所以最优解在"尽量靠近角点但不越界"的地方。模型三次都直接走到那个位置，随机采样三次落在相邻一档。

我不认为这证明了模型"理解"电路。但它确实比均匀随机更快地收敛到正确区域，而且它输出的 `search_hypothesis` 字段能读——比如它会说"沿相位裕量方向抬高 Rcomp"，这个方向是对的。

**Q：如果 LLM 完全不可用（比如 API 挂了），系统还能跑吗？**

能。`propose_fn` 是一个 Protocol，随机采样、脚本注入固定候选、网格枚举都能接进去——对照实验就是这么做的，同一个 `run_task`，只换提案来源。这也是为什么对照实验的可信度比较高：被对照的变量恰好只有一个。

### B. LLM 工程

**Q：怎么保证模型输出可用？**

分三层：

1. **格式层**（`agent/schema.py`）：只管形状。JSON 能不能解析、必填字段在不在、候选数量在 [3,6] 内、参数是不是正数。不校验合法域和档位——那是下一层的事。也**不做 markdown 剥壳容错**，因为一旦容错，格式遵从度就永远测不出来了。
2. **语义层**（`agent/validate.py`）：单位归一、合法域、档位对齐（相对容差 1e-6）、与已测点的距离。**不静默吸附也不裁剪**——偏离档位一律拒绝。吸附会让模型学不会精确输出，而且被吸附点与意图点是两个不同的设计，落库时记成了后者。
3. **物理层**：仿真 + 约束判定。

被拒候选带具名原因（`out_of_domain:rcomp` / `off_tick:ccomp` / `duplicate_of_tested`）落 `rejections` 表，并关联到产生它的那次 `llm_calls`。这样"一次通过率"能算，拒绝原因的分布也能看——`off_tick` 占比高说明模型抄不准档位，要改 prompt 里档位表的呈现；`duplicate_of_tested` 占比高说明它没在看已测点，要改历史信息的组织方式。这两件事的改法完全不同，合并成一个"失败率"就无从下手。

**Q：两类失败为什么要分开计数？**

`max_llm_repair_rounds` 管格式失败（回灌错误清单让它重答），`max_network_retries` 管网络失败（指数退避）。共享一个计数器会**双向坏事**：网络抖动几次就耗尽了模型的修复机会，模型答错几次又会触发无意义的网络重试。而且这两个数字对项目的意义完全不同——一个衡量模型质量，一个衡量环境稳定性。

`llm_calls` 表里 `outcome` 保留了区别：`schema_invalid` 和 `empty` 都表现为"本轮无候选"，但前者说明模型答不出合格格式，后者说明网络重试耗尽根本没答上。

**Q：上下文怎么压缩的？**

波形有 35007 个采样点。我不做 token 截断，而是**按信息压缩**：确定性提取 6 个特征（超调、下冲、恢复时间、纹波幅值、振荡频次、发散标志），采样点禁止进入 prompt。压缩比 35007 → 6。

这不是为了省钱，是因为原始采样点对"下一步该往哪走"这个决策没有信息量——决策需要的是"下冲多深、恢复多久"，那正是这 6 个特征。

**Q：prompt 的可复现性怎么做的？**

相同 `SearchState` 产出逐字节相同的文本和 `context_hash`。两个细节：

- `context_hash` 取自**规范化状态**而不是文本。取自文本的话，排版调整就会改哈希，同一个状态在改了文案之后不再等价——而缓存与复现判等依赖那个等价关系。
- 排除了 `candidate_id` 和 `run_ids`：它们是随机生成的，进哈希就让"相同状态"永远不可能出现两次。

prompt 和原始输出都落盘，`prompt_hash` / `context_hash` 存 `llm_calls` 表。

**Q：为什么 prompt 用 f-string 拼而不用模板文件？**

外置成模板文件，代码与文件之间就多了一层隐式约定：模板里引用了某个字段而代码没提供，或者反过来，没有任何检查会失败。留在代码里，字段名写错是 `NameError`。

报告那边相反，用了 Jinja2——因为报告有十个段落、大量表格、还要按轨道二选一渲染，那个复杂度值得模板引擎，而且我给它配了 `StrictUndefined`：模板写错一个键会直接报错，而不是静默渲染成空字符串。报告里一格悄悄空掉是最坏的结果。

### C. 怎么知道 LLM 真的有用

**Q：你怎么证明不是碰巧？**

三件事：

1. **有参照系**。144 点全部跑完，36 个可行点排好序。"命中第 1 名"是确定的事实，不依赖任何统计假设。
2. **单变量隔离**。对照跑的是同一个 `run_task`，同一份配置、同一套档位、同一个校验器、同一条双层仿真路径、同一组硬约束、同一个停止判定。只换 `propose_fn`。
3. **重复运行**。模型跑 3 次，随机跑 5 个固定种子（种子写在记录里，可原样复现）。

**Q：为什么不比较"用了多少次仿真"？这不是 Agent 最直观的价值吗？**

因为单次运行的这类数字没有统计意义——同一个模型跑两遍就能给出不同的答案。要谈它需要多次重复取分布，而我只跑了 3 次，不够。

项目里我把这条做成了硬性约束：报告模板和渲染产物中不允许出现 `regret`、`simulations-to-target`、"搜索效率"、"收敛速度" 这四类表述，由 `tests/unit/test_report_wording.py` 断言。还有一条相关的：`runs` 表派生的过程量（首次可行解轮次、可行候选率、重复率）不允许进入结论段的渲染上下文——它们可以出现在"过程埋点摘要"段，但不能给设计结论背书。

这条约束的实现方式值得说：**不能靠"模板里别写"**。Jinja2 的作用域是继承的，`{% include %}` 也继承父作用域，所以只要结论段是主模板的一部分，它就能取到过程量。我的做法是结论段用独立命名空间单独渲染成字符串，再作为一个变量传回主模板——过程量根本不在那次渲染的命名空间里，模板写了会因 `StrictUndefined` 直接报错。测试断言的是这个**机制**，不只是"真模板恰好没写"。

**Q：那这个项目的价值到底是什么？**

不是"LLM 找到了最优解"——随机也能找到够好的解，单说这个撑不住追问。价值在于**这套系统能诚实地做出并证伪关于 LLM 有效性的判断**。我在实验记录里同时写了三条限制：达标线区分不出两者、样本量小、空间小。

如果对照结果反过来（随机也能稳定命中最优），这套系统会照样把它测出来，我也会照样写进 README。这是我认为更值得展示的能力。

### D. 电路与仿真（够用即可，不必深挖）

**Q：为什么是电流模式而不是电压模式？**

这决定了整个优化问题是否成立。低压大电流的 LC 输出网络阻尼极小（Q ≈ 4），电压模式下这对双极点在穿越频率处贡献 −180°，而 Type-II 补偿器只有一个零点、最多补回 +90°，**无论怎么整定都拿不到 45° 相位裕量**——那样设计空间里没有一个可行点，寻优就没有意义了。想靠输出电容 ESR 零点补相位，就得把 ESR 加到 mΩ 量级，而那时 `ESR × ΔI` 的瞬时压降会吃光全部电压容限。

电流内环把电感极点消掉、功率级降为一阶，Type-II 才够用。我也考虑过 Type-III，但那会让设计变量变成 4~6 个，超出这个项目想解的二维问题。

**Q：为什么要分筛选层和评价层？**

成本梯度是实测的：平均模型 7.5 ms，开关模型 360 ms，相差 48 倍。筛选层用平均模型快速排除明显不可行的候选，只有幸存者进评价层。

但这里有个前提必须先证明：**两个保真度描述的是同一个电路**。我做了双模型一致性核对——稳态输出偏差 0.0048%（容差 0.5%），负载阶跃下冲偏差 8.25%（容差 10%）。这份核对抓到过一个真实错误：我最初把电流环的采样延迟写成 `0.5/fsw`，正确是 `0.5/(N·fsw)`（4 相轮流采样，有效采样率 ×N）。错值使平均模型系统性悲观约 20%。

值得说的是我当时的推理：**偏悲观不等于安全**。筛选层会误杀实际可行的候选，而被误杀的候选根本进不了评价层，也就没有机会被纠正。

**Q：指标计算怎么验证的？**

用解析已知的构造波形，按 `metrics.yaml` 的文字定义**手算期望值**，再跑实现比对。顺序很重要——这个顺序抓到了一个滤波器边界伪影 bug：原实现用 `np.convolve(mode="same")`，两端零填充，而纹波指标取窗口峰峰值，边界的虚假下沉被全额计入。稳态恒定 0.804 V（真实纹波 0）时报出 0.402 V 的纹波。误差与信号绝对值同阶。

如果反过来做——读实现再写期望值——这个 bug 抓不到，因为期望值会跟着错误实现一起错。

### E. 工程实践

**Q：怎么保证结果可复现？**

- 同一候选同一场景两次求解逐位相同，且与仿真总时长无关。
- 模型依赖闭包的全部文件内容参与 `model_package_hash`，与冻结记录不符即拒绝启动。
- 两份门禁证据记录（裕量交叉核对、双模型一致性）内容是确定性的，sha256 被配置绑定。CI 每次重跑这两个脚本并比对哈希——**这一步不是在检查代码，是在检查那两条门禁本身还成不成立**。一份每次重跑都变哈希的记录会迫使配置跟着改，那等于没有门禁。

**Q：冻结记录为什么不让程序自动创建？**

让跑不通的程序自动补一条冻结记录，等于让被校验方自签通行证。`run_task` 只校验冻结记录，从不创建。测试和脚本里写冻结是在模拟人工审批动作，那件事本身在真实流程里需要人。

**Q：项目里你觉得做得最不好的是什么？**

三个：

1. **设计空间太小**。二维 144 点，随机采样跑几轮就能覆盖一两成，所以区分不出方法的优劣。如果重做，我会选一个至少四维、档位更密的问题——但那需要重新设计约束集，让可行域不至于空。
2. **对照的样本量不够**。3 次和 5 次只能支持很弱的结论。真要谈方法优劣需要几十次，那是几小时的 API 调用。
3. **审批链没打通**。`poweragent report --approve` 需要一个从数据库聚合 9 个字段的 `result_hash`，我把它排在了报告渲染主路径之后，最后没时间做。它不影响渲染，但"人工审批留痕"这个闭环是缺的一环。

**Q：如果给你更多时间，下一步做什么？**

先把样本量补上——那是最便宜的可信度提升。然后把设计空间扩到四维（加上电流环的两个参数），看模型在更大空间里还能不能稳定命中最优；那时"参考扫描"会变得不可行（4 维 12 档是 20736 点），参照系得换成别的东西，这个问题本身就有意思。

## 四、可能被问到的陷阱题

**Q：这个项目有多少行是你写的，多少是 AI 生成的？**

诚实回答实际情况。可以补一句：判断在我这里——比如"采样延迟漏了相数"、"约束集缺了增益裕量"、"结论段上下文必须结构性隔离"这三件事，都是我在跑通之后从数据里发现并推理出来的，不是任何工具替我做的。

**Q：`simulation_only=true` 是什么意思？这个项目能用于生产吗？**

不能，我也在 README 里明确写了。物理数值是自洽的设计假设，量级取自低压大电流 VRM 的常见区间，未绑定实测数据或器件 datasheet。所以结论的效力止于"这套搜索方法在该电路上有效"，不构成选型或打板依据。报告的第一节就渲染这条边界声明，模板里**不存在**渲染"可打板""实物可行"这类表述的分支——是构造上没有那条路径，不是渲染完再过滤。

**Q：为什么裁掉了那么多模块（校准、检索、鲁棒性…）？**

时间预算是 15 天、每天 5 小时。我的判断是：LLM 闭环必须做完做透，其余能砍。被砍的五个模块里，检索和校准是锦上添花，鲁棒性和寄生敏感性属于"有了可交付设计之后才需要"，双模型运行期门禁在当前配置下本就不触发。裁剪理由记在设计文档里，不是"待补全"。

宁可一条链路端到端跑通，不要五条半成品。
